# 调查：语音转写/润色结果繁简不一致

> 状态：**已实现（v1.6.0）**。新增 `voxscribe/script_normalize.py`（OpenCC）+ 设置「中文输出」（默认简体/繁体/保持原文）；ASR 原文与最终稿都会转换；prompt 增加简繁硬性规则。实现后的实测：默认简体的 4 条历史繁体录音，原始转写和最终稿繁体字数均为 0；`preserve` 模式保留原文。
>
> 调查日期：2026-10-23 · 机型：RTX 5060 Laptop + Intel Core Ultra 7 255HX · 模型：faster-whisper medium（CUDA float16）+ DeepSeek `deepseek-flash`

## 一、结论摘要（按影响排序）

| 排序 | 根因 | 证据 | 影响 |
| --- | --- | --- | --- |
| 1 | **ASR 自动语言模式没有加简体 initial_prompt** | 30 条真实录音：`language=auto` 有 4 条输出繁体（共 90 个繁体字）；`language=zh` 有 0 条繁体 | 原始转写阶段就会混入繁体 |
| 2 | **DeepSeek prompt 没有硬性简繁规则** | 同一段繁体原文，走当前「直出」prompt 重跑 6 次：2 次仍保留 12 个繁体字、4 次变简体；加一句「一律输出简体」后 6/6 都是简体 | 润色阶段时好时坏，与用户观察一致 |
| 3 | **没有简繁后处理/归一化步骤** | 全项目没有 OpenCC / t2s 调用；转写和整理结果原样显示、原样复制/导出 | 前面两处任一漏掉繁体，最终结果就带繁体 |
| 4 | **两段式展示先显示 ASR 原文** | `_on_quick_transcript` 先把原始转写显示到结果框，再被整理稿替换 | 用户可能看到/复制到中间态的繁体；也会造成"有时繁体"的观感 |
| 5 | **缺少简繁设置项** | `language` 只控制识别语言（auto/zh/en…），没有"简体/繁体"选项 | 无法让用户固定输出字形 |

## 二、实测数据

### 2.1 真实录音逐条对比（同一音频、同一模型）

- 取样：`data/recordings/` 下 30 条有效录音（1 秒以上）；
- 对比：`language=auto`（无 initial_prompt） vs `language=zh`（带 `以下是普通话的会议记录。`）；
- 繁体统计：用 OpenCC `t2s` 做基准，统计转换后发生变化的字符数（近似繁体字符数）。

结果：**只有 `auto` 模式出现繁体，`zh` 模式 0 条**。

| 录音 | 时长 | auto 检测语言 | auto 繁体字数 | zh 繁体字数 |
| --- | --- | --- | --- | --- |
| 录音_20261022_184232.wav | 47.5s | zh | **42** | 0 |
| 录音_20261022_210053.wav | 18.6s | zh | **11** | 0 |
| 录音_20261022_212050.wav | 22.6s | zh | **31** | 0 |
| 录音_20261022_213434.wav | 8.1s | zh | **6** | 0 |
| 其余 26 条 | — | zh / 空 | 0 | 0 |

> 空语言是静音/无有效语音的录音，与本次问题无关。

### 2.2 DeepSeek 润色阶段的随机性

对上面 11 个繁体字的样本，走当前「直出」prompt（`reasoning_effort=none`）重复请求 6 次：

| 条件 | 6 次输出的繁体字数 |
| --- | --- |
| 当前「直出」prompt | 0, **12**, 0, 0, 0, **12** → 2/6 仍带繁体 |
| 额外加「无论原文是否繁体，一律输出简体中文」 | 0, 0, 0, 0, 0, 0 → 6/6 简体 |

同一段原文、同一 prompt，两次结果不一致 → **模型输出本身存在随机性**，仅靠提示词无法 100% 保证。

### 2.3 后处理方案验证（OpenCC）

对 4 条 auto 模式的繁体转写直接做 `t2s`：

- 4/4 全部转成简体，字数不变；
- 100 次转换耗时 0.05 秒，典型文本 <1ms；
- `opencc-python-reimplemented` 包体积约 **1.1MB**，import 约 21ms（符合本软件轻量目标）；
- 对英文/数字/标点无副作用（只改中文繁体字）。

## 三、代码链路定位

1. **ASR（原始转写）**
   - [asr.py](D:/Project/voice2text/voxscribe/asr.py#L95) 定义了 `ZH_INITIAL_PROMPT = "以下是普通话的会议记录。"`，注释明确说明它能"把繁体输出拉回简体"。
   - [asr.py](D:/Project/voice2text/voxscribe/asr.py#L964-L975) 的 `_resolve_initial_prompt()` 只在 `language` 为 `zh` / `zh-*` 时返回该提示；`language=None`（自动检测）**直接返回 None**。
   - 默认配置 `language="auto"` → 首页口述默认走 auto → 没有简体提示 → 部分音频输出繁体。
   - 文件转写页如果选了「中文」，会带提示，所以文件页更少出现繁体。

2. **DeepSeek 整理**
   - [prompts.py](D:/Project/voice2text/voxscribe/prompts.py#L170-L183) 的通用规则只有"输出语言：简体中文"和"保持原文语言、不要翻译"，**没有"禁止繁体/强制简体"的硬规则**；"保持原文"反而可能被模型理解为保留字形。
   - 「直出」prompt 要求"保留原话、不要改写"，模型更倾向照抄原文的繁体字。
   - 模型采样存在随机性（见 2.2），相同输入两次输出可能一个简体、一个繁体。

3. **后处理**
   - 项目中没有简繁转换代码；`Transcript` / `RefineResult` / 导出（txt/md/docx/srt）/ 剪贴板均原样传递。

4. **界面**
   - [app.py](D:/Project/voice2text/voxscribe/gui/app.py#L1458-L1466) 的 `_on_quick_transcript()` 会先把 ASR 原始文本显示到结果框，等 DeepSeek 返回后再替换。用户如果在这期间看到/复制文字，会看到繁体中间态；而最终稿是否简体仍取决于模型。

5. **设置**
   - [config.py](D:/Project/voice2text/voxscribe/config.py#L83) 只有 `language`（auto/zh/en/ja/ko），没有输出字形（简体/繁体）选项。
   - 手动术语表（`glossary`）本身如果写了繁体词，也可能把繁体带进模型输出。

## 四、修复方案

### P0（推荐，确定性根治）：增加简繁后处理

- 新增依赖 `opencc-python-reimplemented`（约 1.1MB，轻量）。
- 新增设置 `chinese_script`：`simplified`（默认）/ `traditional` / `preserve`。
- 在以下位置统一转换（仅当检测/配置语言为中文时）：
  1. ASR 完成、返回 `Transcript` 之前 → 原始转写即简体（两段式展示也一致）；
  2. DeepSeek 返回后、显示/复制/导出之前 → 最终稿一定符合设置；
  3. 文件页导出与剪贴板共用同一份最终文本。
- 转换只改字形，不改内容；英文/数字/专业术语不受影响。
- `preserve` 模式保留现状（给需要看原文繁体的用户）。

**验收标准**：同一批 30 条录音，auto 模式原始转写 + 最终整理稿的繁体字数全部为 0（`preserve` 模式除外）；中译英/英文录音不受影响。

### P1（减少模型随机性）：prompt 加固

在 [prompts.py](D:/Project/voice2text/voxscribe/prompts.py#L170) 通用规则中增加一条：

> 中文输出一律使用简体中文，不得输出繁体字；即使原文是繁体，也要转成简体（专有名词按常用简体写法）。

- 对「直出」模式尤其重要（它最容易照抄繁体）。
- 如果支持 `traditional` 设置，则改为按设置生成对应规则（简体/繁体二选一）。
- prompt 只是"降低概率"，不能替代 P0；两者结合效果最好。

### P2（ASR 策略与可观测性）

- 自动语言模式下，可在转写后用 `info.language` 判断：若检测为中文，则在「显示前」做 P0 转换；无需强制给 auto 加中文 prompt（避免影响英文/日文检测）。
- 日志记录：检测语言、`language_probability`、原始转写繁体字符数、最终稿繁体字符数（只记数字，不记正文）。
- 两段式展示改为"ASR 原文先按字形设置转换再显示"，避免中间态引发误解。

### P3（可选）：默认语言策略

- 若用户以中文为主，可在设置里把「音频语言」固定为「中文」，这样 ASR 会带简体 initial_prompt，从源头减少繁体；但会失去中英自动检测，建议保持 auto + P0 后处理。

## 五、可验证的排查步骤（以后复现/验收用）

1. 用同一段录音，分别用 `language=auto` 和 `language=zh` 转写，比较原始转写（不要看整理稿）——本项目实测 auto 有繁体、zh 没有。
2. 看两段式中间态：ASR 原文是否繁体；若原文简体而最终稿繁体，说明问题在 DeepSeek；反之在 ASR。
3. 同一段文本连续调用 3~5 次 DeepSeek「直出」模式，统计繁体字数——可复现"时好时坏"。
4. 加 `extra_instruction="无论原文是否繁体，一律输出简体中文"` 再跑，繁体概率下降但不会 100%。
5. 用 OpenCC `t2s` 转一次，确认繁体能被完全消除。
6. 检查设置：`language` 是否为 auto；术语表是否含繁体词；用户是否在整理完成前复制过中间态文字。
7. 排查日志建议字段：`detected_language`、`language_probability`、`raw_trad_chars`、`final_trad_chars`。

## 六、风险与取舍

- 繁体用户：默认简体可能不符合预期 → 提供 `traditional` / `preserve` 设置。
- 专有名词/人名：OpenCC 一般按常用字形转换，若用户希望保留特定写法，可用术语表覆盖（P0 转换后再应用术语表本地替换，顺序需明确）。
- 性能：OpenCC 单次转换 <1ms，对口述延迟无影响。
- 依赖：1.1MB，远小于现有 CUDA 依赖；若不想新增依赖，也可只加 P1 prompt，但无法确定性根治。
